# Decisiones técnicas — OpsFlow

### D-01 — Lógica de negocio en PL/SQL, no en la interfaz
**Decisión:** las reglas (cálculo de SLA, transiciones, auditoría) viven en un *package* y
*triggers*, no en procesos de página.
**Motivo:** garantiza que la regla se cumpla **sin importar por dónde entren los datos**
(APEX, un script, otra integración).

### D-02 — Triggers para auditoría automática
**Decisión:** el historial de estados se llena con un *trigger* `AFTER INSERT OR UPDATE`.
**Motivo:** imposible "olvidarse" de auditar; la base lo hace sola. Alternativa descartada:
auditar solo desde el paquete (se saltearía si alguien hace un UPDATE manual).

### D-03 — Vistas para las métricas
**Decisión:** los KPIs y datos de gráficos se exponen como *views* (`vw_dashboard_kpi`, etc.).
**Motivo:** la lógica de agregación queda centralizada y reutilizable; APEX solo hace
`SELECT * FROM vista`. Facilita el mantenimiento y las pruebas.

### D-04 — Claves primarias con IDENTITY
**Decisión:** `GENERATED BY DEFAULT ON NULL AS IDENTITY` en vez de secuencias + triggers.
**Motivo:** es la forma moderna (Oracle 12c+), menos código y menos propenso a errores.

### D-05 — Flags 'S'/'N' con CHECK constraints
**Decisión:** booleanos como `CHAR(1)` restringidos por `CHECK`.
**Motivo:** Oracle (hasta 23c) no tenía tipo booleano nativo en tablas; es el patrón habitual
y deja la integridad garantizada por la base.

### D-06 — Scripts idempotentes y numerados
**Decisión:** los scripts se pueden re-ejecutar y están numerados por orden de dependencia.
**Motivo:** facilita reinstalar el proyecto desde cero.
